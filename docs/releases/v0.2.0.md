# VLT/1 v0.2.0

**Release date:** 2026-08-21  
**Baseline:** `v0.1.0` → `v0.2.0`  
**Scope:** 22 commits covering local-vault streaming, security hardening, witness reliability, deterministic validation, and release engineering.

## Release summary

VLT/1 v0.2.0 is the first substantial development release after v0.1.0. It preserves the project's local, single-owner encrypted-vault profile while adding a binary streaming data plane for large objects, durable operational controls around daemon and filesystem boundaries, strengthened freshness-witness behavior, and reproducible quality/release evidence.

> VLT/1 remains a local Unix-socket vault rather than a network service, policy engine, multi-user authorization system, or generic decryption API. The threat model and deployment requirements remain defined by the tagged `docs/ARCHITECTURE.md` and `deploy/README.md`.

## Detailed changes

### Binary streaming protocol and CLI

The protocol now supports bounded binary stream items alongside the existing closed JSON request/response model. The daemon performs a single authorized stream exchange per connection and applies configured I/O deadlines. The CLI now uses this path for `put` and `get`, preserving output verification before publication while avoiding base64 expansion and the JSON frame-size constraint for bulk plaintext.

The core implements incremental chunk encryption and read-back verification. It constructs the authenticated chunk digest as each encrypted record is produced and retains only the record needed for transaction publication. This eliminates the legacy duplicate encrypted-record buffer during direct `put` preparation.

### Persistence, backup, and filesystem hardening

VLT/1 now enforces owner-private permissions on the primary SQLite database and present WAL/SHM state files. Backup creates a consistent online SQLite snapshot, verifies its structural integrity and vault-ID binding, and writes a sidecar integrity manifest. Restore verifies the source before creating a new inactive output database.

Every sensitive filesystem boundary now fails closed. Vault databases, backup sources and manifests, new backup/restore outputs, daemon socket locations, durable witness state, and plaintext CLI output paths reject symlink endpoints, symlinked lexical parent chains, non-regular existing files, non-directory parent components, and overwrite attempts. These changes preserve the existing no-overwrite publication mechanism based on private temporary files, sync, and hard-link publication.

### Daemon scheduling and local protocol resilience

Long-running operations—binary upload, binary download, active-object verification, and online backup—now acquire a scoped permit. If another long operation is active, later requests are rejected promptly with the protocol `Overloaded` code. This prevents a slow client stream from creating an unbounded mutex wait for independent local callers.

The daemon continues to cap concurrent connections, require same-user Linux peer credentials, and use bounded read/write deadlines. New regression tests cover overload behavior, delayed stream cleanup, and unsafe socket-parent paths.

### Freshness witness integrity

Strict witness configurations can now include one temporary prior Ed25519 public key for a planned signer rollover. Receipts signed by any other key remain rejected. This allows controlled key replacement without weakening the pinned primary-anchor model.

Witness integration tests now wait for a bounded listener-readiness condition rather than relying on an arbitrary startup delay. The durable witness SQLite state also receives the same pre-open path hardening applied to other VLT/1 sensitive state.

### Validation, CI, and release engineering

v0.2.0 adds deterministic fixed vectors for canonical Manifest encoding, cryptographic AAD transcripts, encrypted-chunk digests, and witness signing material. The parser attack surface is covered by bounded ASan fuzz regression targets for both Manifest decoding and IPC decoding.

The repository enforces formatting, warnings-as-errors Clippy, workspace tests, fault-injection tests, release builds, locked Rust 1.75 compatibility, and dependency/license policy checks. Tag releases produce a deterministic Linux x86_64 bundle with SHA-256 checksum, SPDX SBOM, and GitHub attestation.

## Compatibility and upgrade notes

| Topic | Guidance |
|---|---|
| Release numbering | This is a `0.y.z` development release. The move from 0.1.0 to 0.2.0 communicates substantial new functionality rather than a patch-only correction. |
| Existing vaults | Existing VLT/1 databases should be opened only through the tagged binaries after a normal backup and restore drill. The vault remains locked until the passphrase succeeds and active objects still require authenticated verification. |
| Local protocol clients | Legacy JSON requests remain part of the profile. Clients consuming the public Rust protocol enums should recompile against v0.2.0 so that new request, response, stream, and error variants are handled deliberately. |
| Large files | Use the tagged `vlt1 put` and `vlt1 get` clients for binary streaming; do not raise the JSON protocol frame limit. |
| Filesystem paths | Replace symlink-based operational paths with direct paths under real owner-controlled directories before deployment. New outputs must not already exist. |
| Witness rollout | Configure a previous public key only for a deliberate temporary signer rollover. Remove it after every vault has observed receipts under the primary anchor. |

## Validation

The v0.2.0 tagged source passes the release workflow's formatting, strict Clippy, workspace, fault-injection, release-build, locked MSRV, and dependency/license checks. The release bundle is generated from the locked dependency graph and includes provenance and SBOM attestations.

## Security boundary

VLT/1 does not claim protection against root or kernel compromise, process-memory disclosure, physical side channels, malicious dependencies, or rollback when no correctly independent witness is configured. Consumers must review the tagged deployment documentation before use.
