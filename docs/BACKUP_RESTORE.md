# VLT/1 backup and restore

**Author:** Itan Winter (NIxort) / Nixort

VLT/1 supports only a **consistent encrypted SQLite snapshot** produced through SQLite's online backup API. A raw `cp` of a live vault database is not a supported procedure because a WAL database may have state outside the main database file. SQLite documents that an online backup yields a consistent snapshot and permits other users of the source database to continue between incremental backup steps.[1] The `rusqlite` API used by VLT/1 is a direct implementation of SQLite's incremental online-backup pattern.[2]

## Backup procedure

The daemon serializes an online backup with vault operations. The operation does not decrypt plaintext and may run while the vault is locked. The destination and its sidecar must both be new paths.

```bash
vlt1 backup --socket /run/user/1000/vlt1d.sock \
  --output /secure-backup/vault-2026-08-17.sqlite
```

The command produces two mode-`0600` files.

| Artifact | Purpose |
|---|---|
| `vault-YYYY-MM-DD.sqlite` | Consistent encrypted SQLite snapshot generated by the online backup API. |
| `vault-YYYY-MM-DD.sqlite.vlt1-backup.json` | Non-secret VLT/1 manifest: format marker, vault ID, SHA-256 of the snapshot, and exact byte length. |

Before publication, VLT/1 runs `PRAGMA integrity_check`, `PRAGMA foreign_key_check`, and verifies that the snapshot `vault_meta.vault_id` equals the ID placed in the sidecar. The sidecar is an **operational integrity manifest**, not a signature: an attacker able to replace both it and the encrypted snapshot is still constrained by VLT/1 AEAD verification on unlock, but may replay an older valid snapshot. Configure the independently operated external witness for rollback detection.

## Restore procedure

Restore is intentionally an **offline** procedure. Stop `vlt1d` first. The command refuses to overwrite the output and restores through SQLite's backup API after validating the source manifest, SHA-256, byte length, database integrity, foreign keys, and embedded vault ID.

```bash
systemctl stop vlt1d@alice.service
vlt1 restore \
  --backup /secure-backup/vault-2026-08-17.sqlite \
  --output /var/lib/vlt1/vault-restored.sqlite
# Validate the replacement database before changing a service configuration.
vlt1d --vault /var/lib/vlt1/vault-restored.sqlite \
  --socket /run/user/1000/vlt1d.sock
```

An operator must test the restore on a separate path, unlock it with the correct passphrase, run `vlt1 verify`, and—when strict witness mode is enabled—confirm a challenge-bound external witness head before treating the restored vault as current. A healthy backup has not been proven recoverable until this drill succeeds.

## Safety rules

| Rule | Reason |
|---|---|
| Keep backup storage and the witness state under independent operational control. | Co-restoring both systems defeats rollback evidence. |
| Retain the backup database and sidecar together. | The restore command verifies their binding before creating an output. |
| Never overwrite a running daemon-owned vault database. | VLT/1 deliberately requires a stopped daemon and a new destination to avoid accidental live replacement. |
| Use direct regular-file paths for vault databases, backup sources, manifests, and new backup/restore outputs. | VLT/1 rejects symlink files and non-regular filesystem objects at these security boundaries, preventing accidental path indirection. |
| Place vault, backup, restore, and daemon socket paths below real existing directories with no symlink component. | VLT/1 rejects symlinked or non-directory path parents before opening, creating, unlinking, or binding a sensitive artifact. |
| Use encryption at rest for backup media. | The VLT/1 snapshot remains application-encrypted, but metadata, access patterns, and passphrase envelope remain sensitive operational assets. |
| Rehearse restores after every deployment or storage-policy change. | A successful snapshot does not prove permissions, passphrase availability, witness access, or operator steps. |
